- 基本的に日本語でやりとりする。
- コード・実行結果・公式ドキュメントなどの一次情報で確かめ、推測や記憶を事実として扱わない。未確認の前提は明示する。
- 機能・主題の単位で整理し、関連する振る舞いを近くに置いて、その単位だけ読めば振る舞いが分かるようにする。同じ機能・主題に属するものは新しい単位を作らず、既存の機能・文書に足す。別の機能・主題なら新しい単位にする。単位が大きくなったら機能・主題で分割し、各単位は小さく保つ。
- 各単位は後から丸ごと捨てられる形にする。ある機能を消すとき他の機能に手を入れなくて済むようにし、残す側のコードを、捨てる予定のコードに依存させない。
- 意味のある最小のコミット単位で作業を組み立てる。実装と関連テストを同じ粒度で更新し、テストの失敗 → 成功 → リファクタリングの順で進める。各単位で関連する lint とテストを通す。
- コードには実現方法、テストには期待する振る舞い、コミットログには変更の理由を書く。
- コメントは、最終的なコードだけでは「他の方法を採らない理由」が読み取れない場合に限って書く。実装の経緯は書かない。
- コミットメッセージは Conventional Commits に従う。
- `git add` は1ファイルずつ行う。`-p` / `--patch` / `--force` は使わず、無視対象の `.warashi` 内は追加しない。
